# 分组维度与展示字段重复输出修复

## 原问题与根因

原问题：统计美敦力、波士顿科学在二级医院的销售额。

原请求范围为模型 130、业务域列表为空；原 ASL 时间范围为 2025-10-28 至 2026-10-28。2026-10-28 16:55 的服务日志确认：结构化参数和 ASL 已通过，SQL 翻译报“列别名重复: 医院等级”，未执行业务查询。

**PROVEN**：枚举维度生成 CASE 标签列，展示字段生成同一属性的物理列。旧实现仅按表达式去重，两种表达式不同，却用了同一结果列名。通用异常响应还丢失了这个明确原因。

## 变更范围

- SELECT 构建保留维度与展示字段的角色。展示字段的物理来源、时间粒度和列名都与已输出分组列一致时复用该列，保留枚举标签及编码。
- 不改变 ASL、授权范围、过滤条件、指标公式、Join 或 GROUP BY。不同字段或不同时间粒度的同名列仍拒绝执行。
- 明确的重名异常返回 `DUPLICATE_OUTPUT_COLUMN`，指出重复列并说明查询未执行。未知异常仍不向用户泄露内部异常内容。
- 将原问题按原文加入业务问题回归清单。

## 真实验证与边界

原故障日志中的同一份 ASL 经只翻译接口重放：修改前失败；候选版本成功，医院等级标签恰好一列，枚举编码与分组均保留。这是确定性复现的补充证据，不能替代端到端验收。

原问题经正常 `/agent_chat` 入口在隔离候选环境完整执行，返回两个品牌的两行结果、销售额和图表。品牌、二级医院、原日期范围及金额排序均保留。最终回答明确提示数据实际覆盖至 2025-12-30，没有声称完整覆盖请求时段。

原版本重新提问也可能成功，因为模型有时只选择品牌维度，不生成医院等级重叠列。故不能仅凭一次重问是否成功判断缺陷是否修复。

19 条业务问题清单均检查可运行条件；其中 7 条具有明确原请求范围，以并发 2、独立会话执行原版本与候选版本对比。其余 12 条尚未恢复原请求授权范围，不使用默认模型替代；另有 9 条历史上下文不完整的问题保留在 `unresolved_context` 中。

候选环境与原版本均为 6 条 `COMPLETED`、1 条 `NEEDS_CLARIFICATION`，不等于 7 条业务全部验收通过：

- 当前原问题、两品牌原有问法、按品牌展示厂家：均执行完成，分别返回 2、2、12 行。
- 三级医院计数：执行完成，但仍按有订单医院统计，存在原有口径限制。
- 已发货未开票金额：执行完成，仍需区分目录指标名称与业务口径。
- 上海经销商销售总额超过阈值：两版本均在“上海”标准值匹配阶段请求澄清，尚未进入 SQL 翻译。
- 公司明细：候选返回记录，原版本重跑返回空结果，结构化提取存在波动，不能宣称历史问题完全稳定。
