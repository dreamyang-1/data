# 平均订单金额口径修复与使用复测

## 结论与根因

当前目标是 V1 指标选择与任务规划的最小修复，不推进 V2 切流。修复前，同一个模型规范同时登记了两类口径：平均每单销售金额为金额除以订单笔数；订单级均价为按订单汇总后的金额除以商品数量。两者都可拥有合法的目录登记，不能因为登记名有效就认为符合用户问题。

PROVEN：原句“给出2025年订单平均金额最高的前五位销售人员，以及他们所在的销售公司”不在模型 130 的登记同义词内。实际任务规划选择了订单级均价，并按业务员、订单号展开，分母成为销售总数量；明确改写为“平均每单销售金额”后，规划选择了订单笔数作分母。两次提问措辞不同，不能把这组观察描述成同句必然随机波动。模型内部选择动机不能直接观察，但缺少问题分母口径复核这一代码缺口已证实。

PROVEN：错误口径的两个 SQL 均已执行成功，随后各 59,383 行结果超过 Dataset 的 10,000 行内存合同，组装数据集失败。第三个任务因前置任务失败而跳过。因此，调度器不存在“固定不执行第三个任务”的证据。原句这一实例的最早偏差在指标选择，结果容量问题使它进一步表现为第三任务未计算。

模型边界也必须区分：本次只读核对中，模型 81 未登记平均每单销售金额，模型 130 已登记。81 的未知均价绑定不能一概判成程序缺陷，不能借用 130 的指标扩大当前请求范围。

## 本轮修改

- 新增以当前模型规范为依据的平均金额合同。依据登记公式、单位、计数指标及对象名称区分“金额÷对象笔数”和“金额÷商品数量”，输出候选仍为现有登记原名，没有写入新同义词或业务字段。
- 在任务参数提取前，校验确定性展开后的交付指标。若模型遗漏目标或用另一种分母的均价替换，沿现有机制反馈纠错一次；仍不符合时拒绝执行，不把错误口径送入取数。
- 保留明确指定的订单级均价、按数量计算的公式、口径解释、逐笔订单金额、多个明确指标及现有任务边界补全。多个登记候选不能唯一对应时不代替用户选择。
- 运行修改仅涉及任务规划器的一个函数及一个新增模块；ASL 向量标准字段和值匹配、Scope、SQL 校验、Dataset 容量及其他既有行为继续使用原有合同。

## 广度检查中发现的其他现象

以下保留为已知问题，不随本次指标口径修改扩展调用链：

1. PROVEN：覆盖率问题重复出现“覆盖率”时，安全关键词规则会命中“覆盖”，把正常查询误判为修改操作。原生请求与实际生产函数的独立调用均已复现。
2. PROVEN：合成输入中，前置结果缺少公司展示属性时，本地计算修补器会把整个任务改写为明细查询，移除结果操作但保留计算交付要求。已有输入包含展示属性、明确禁止再查库以及已绑定登记公式的对照行为得到保留。它不是所有计算任务都会发生的故障。
3. PROVEN：模型可以生成不符合执行器 Schema 的 postprocess；后续较完整的参数操作又会被这个结构覆盖。本轮没有放宽执行器校验来接受未知指令。
4. PROVEN：在原始快照上，部分请求达到总超时后仅返回流错误，没有完整最终回答；并发样本还出现 ASL 容量耗尽。单独复跑后的通过不能证明这些性能问题已消失。
5. PROVEN（合成数据）：最终汇总选择列表仅含一个成功任务时，另一独立问题的成功结果可能被遗漏。本次两项独立排名的真实接口样本完整交付，不能把合成复现说成该真实样本已经漏答。
6. PROVEN：原始快照的单查询成功分支曾缺少最终输出标题，零结果分支也存在主节点展示不齐；应与复合任务的七阶段完整样本分别评价。
7. PROVEN：回答中出现业务编号均值、把每单写成每单位、未证实的专项订单/退货原因及“缺失数据对排名影响极小”等表述。聚合数据和水位不足以支持这些原因或稳定性结论。低金额样本的叙述还存在金额舍入不一致。后续应按证据约束报告，不以本轮数值计算通过代替文字验收。
8. 早期快照的公司名称关联结果缺失，样本已如实说明。保留服务器并行更新后的最新隔离样本已返回公司字段；本轮没有修改业务数据、目录或关系，不将这一变化归功于本次指标选择修复，仍需依据实际执行证据核对。

本次通过与前端同用的原生流式接口复测，并检查实际任务计划、SQL/计算状态及最终回答；未将其称为浏览器图表渲染和所有附件内容的完整验收。诊断产物只提交计划状态、计数、哈希及验证结论，不提交业务明细、原始日志或签名链接。
