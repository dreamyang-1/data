# 复杂组合问题的规划、执行与交付：研究及近期修改规划

研究日期：2026-10-19。版本仓基线：`8f26219`。本轮实读本地开发代码，并浏览开源项目官方文档与源码；没有修改功能代码，没有访问生产数据库或发布服务。9月16日《分析报告.md》仅作为历史材料，没有将其中旧行号、数量或结论直接当成当前事实。

## 1. 判断与近期目标

现有代码已经有“独立交付问题 → 每个问题内部的任务 DAG”两层结构，也有依赖跳过、检查点、澄清恢复、结果复用和统一汇总。问题主要出在这些环节之间的合同没有完全贯通。继续只补拆分提示词，不能解决已经复现的依赖错指、错误复用、计算选错列和回答覆盖缺口。

需要分开回答的问题，并不一定在数据上互相独立；一个问题也不等于一次 SQL。查询、依赖上游名单后的新查询、已有数据计算、口径解释和最终回答，是不同的职责。规划层可以给出意图与逻辑任务，执行层必须根据真实输入、授权范围和数据完整性确定能否执行。

**近期总目标：在现有规模和接口内，打通复杂组合问题从两级规划、依赖绑定、ASL/SQL或已有结果处理，到逐问题完整交付的最小可靠闭环。**

分成三个可分别完成的阶段。建议下一次 Goal 只完成阶段1：先修可能静默产生错误数字的复用与计算路径；阶段2修两级规划依赖；阶段3补齐逐问题交付及恢复验证。完成一个阶段后报告并停止，不把框架迁移、全目录发布或任意规模规划混入同一个 Goal。

## 5. 修改后的业务与执行合同

### 5.1 两层身份与交付

保留原问题的业务目标、条件和交付要求。问题归属不能只靠任务数组偏移；内部需要稳定的问题身份或等价映射。一个问题关联一个或多个任务，一个任务的结果可以供其他问题消费。共享结果必须保留消费关系，不能因去重导致原问题消失。

不强制增加外部API字段或固定回答标题。优先使用已有结构和内部映射；只有现有模型无法表达正确行为时，才增加有兼容默认值的内部字段。模型可建议展示哪些中间结果，但不能决定忽略哪个已接受的独立业务问题。

### 5.2 任务路径与ASL/SQL

| 任务路径 | 需要的真实输入 | ASL与业务数据库行为 | 不满足条件时 |
| --- | --- | --- | --- |
| 新业务查询 | 完整问题、当前Scope、结构化参数及目录证据 | 先按现有ASL服务绑定/校验，再由SQL Translator生成并执行查询 | 语义不明确则澄清，服务失败按已分类错误处理 |
| 依赖结果后的新查询 | 上游确定结果及ID/列/值集合、目标实体、原问题条件 | 先编译依赖约束，再走ASL和SQL；依赖名单并不代表不查库 | 空结果、截断、缺稳定键、绑定不明确时停止该后继并说明 |
| 已有结果的筛选/排序/计算/连接 | 指定数据集、列、操作、粒度及完整性 | 使用现有本地计算能力；不发新的业务查询，也不制造伪SQL成功记录 | 数据不足时说明或澄清；用户要求不查库时不得暗中补查 |
| 口径/来源/解释 | 已登记语义、元数据或已验证业务结果 | 走对应元数据/直接回答路径；如问题还要求数值，则数值部分仍需查询或真实结果 | 无登记依据时明确未确认，不编造口径 |
| 最终交付 | 问题级状态、终端任务输出和证据 | 汇总已有结果，不让回答模型代替数据库或确定性计算 | 每个问题提供答案、待确认项或失败原因 |

所有依赖不能在规划时仅变成一句“根据上述结果”。应明确消费哪个上游结果、哪些列/键、用于什么约束或计算。上游只用于参数的任务，与直接复用上游业务数据的任务，要保持不同的执行语义。

先展示规划，再进入ASL/SQL/工具执行。依赖任务可先公布逻辑任务与待绑定输入；上游完成后再物化真实参数，不能在规划前偷跑查询。失败修复也不能悄悄改变原任务目标和用户限制。

### 5.3 结果复用与计算

复用比较必须覆盖当前请求中真正影响结果的字段：实体、明细投影、指标及聚合、维度、过滤、时间范围/粒度、排序/限行/去重等，并继续走现有授权、会话、模型版本和来源检查。字段排序和格式可以按语义规范化；不要依赖注释声称“所有要素已比较”。数据库身份与当前Scope如何共同生效要一起测试。

“同样问题自动免查库”“用户要求刷新”“明确只用上轮数据”是不同政策。近期先修错误等价判定与源完整性，不顺带发明全局缓存TTL或静默刷新策略。版本/水位证据不足时应记录UNKNOWN或拒绝自动命中，具体新鲜度政策需有业务依据。

计算必须绑定操作、输入数据集、列以及分母语义。单行数据不天然是分母，最后一列不天然是目标指标，最大的结果集也不天然是分子。多数字列、列顺序交换、零分母、缺失值、时间/单位/粒度不兼容都应有明确处理。

优先使用现有 `dataset_source_complete()`、数据集引用、Scope校验和计算执行器。完整性不满足时可以交付有边界的预览，但不得据此计算全量排名、比例或编译完整业务名单。读取到文件全部行，不等于源查询完整；状态也不能无依据提升成PASS/HIGH。

### 5.4 失败、澄清与恢复

独立问题失败不阻止健康问题完成；依赖失败只阻断相应后继。确认空结果、执行失败、数据不完整和等待澄清分别表达。原问题及候选快照必须保留；序号回复恢复原任务，不能作为新问题。

复用已完成检查点时重新核对Scope、计划版本和必要的数据版本。仅继续待确认任务及其受影响后继。已有结果不能被并发分支全量覆盖；新问题不得被旧Pending挟持；取消后防止迟到结果写回新轮次。现有实现有这些能力的部分以保护和验证为主，不再造完整持久化引擎。

## 6. 三个短阶段及停止条件

### 阶段1：先修结果复用与计算的确定性正确性

修复E1/E2，补齐E3/E4边界。优先修改 `_query_fingerprint_components()`、`_reuse_prior_dataset_for_task()`、`_compile_dependency_constraints()`、`_respond_pure_computation()`及直接相关调用；复用既有完整性、绑定和数据集能力。只有复现证明必须跨服务修改才扩大范围。

验收：不同时间/实体/字段不错误命中；等价请求仍可复用；用户刷新与明确不查库行为受保护；多数字列的医院数比例为5%/10%，换列顺序不变；完整且唯一绑定的原正确计算仍通过；不完整、缺键或绑定含糊的数据不产出虚假成功。验证正确路径的ASL/SQL调用次数，而不是只测布尔值或文字。

完成后独立提交、按合同发布并报告。停止，不自动进入阶段2。它只完成执行正确性子目标，不宣称复杂问题全链路已验收。

### 阶段2：修正两级规划、依赖绑定与预算

修复P1/P2/P3，保留12任务上限。建立问题到交付输出/任务的明确映射，合并问题级和组内依赖；在构造模型前处理预算。校验未知引用、自依赖、循环和交付覆盖，不默默删掉原问。依赖约束在输入就绪后传给ASL，避免任务文字与实际查库方式冲突。

验收：多个独立问题各自多任务；前一问题多任务、当前问题多任务、多个上游问题；共享条件和差异条件不串用；恰好12任务可执行，超限在执行前给出可理解的处理；字段绑定与去重不破坏问题归属。允许等价计划，不固定LLM措辞或SQL数量。

完成后独立交付并停止。先前阶段新增回归必须继续通过。

### 阶段3：逐问题交付、局部恢复与端到端闭环

修复D1。问题归属进入根问题材料和覆盖校验；汇总模型选择少量任务时仍保留所有独立问题的交付或明确状态。继续保持当前最终输出风格。把前两阶段接入真实API装配的离线流程，验证ASL、SQL翻译执行、计算及复用证据可追踪。

验收：一题成功一题失败、一题澄清其余完成、依赖空结果、下游计算失败、恢复只继续必要任务、重复回复/并发恢复、取消及Scope变化；全部原问题都有交付状态；节点顺序、Pending原候选、原有正确单问及多轮行为均受保护。

完成后报告这个近期总目标的闭环结果与仍未验证的真实模型/生产边界，不自动启动下一轮架构工程。

## 7. 应冻结的场景矩阵

以下是建议的验收场景，不是已测准确率；各阶段只实现其直接需要的部分。

| 类别 | 必须覆盖的场景 | 关键断言 |
| --- | --- | --- |
| 两层规划 | 两个独立问题，各有查询与计算；同一目标排名后查明细 | 原问覆盖，组内依赖正确；不按“且/另外”机械分问 |
| 条件 | 共享年份/地区，但各题指标、对象或时间不同 | 公共条件继承，差异条件不互相覆盖 |
| 跨组依赖 | 前组多任务、后组多任务、多前置组 | 引用实际交付输出，不把问题索引当任务索引 |
| 查询执行 | 无依赖新查询、名单约束后新查询、缺参数 | ASL只在可绑定时执行，SQL输入有据，未就绪不执行 |
| 非查询执行 | 本地筛选/排序/比例，口径说明 | 不暗中查询新业务数据；结果数值和依据正确 |
| 计算语义 | 多数字列、列重排、零/缺失分母、同名不同单位/粒度 | 明确输入绑定；错误数据不被标HIGH成功 |
| 复用 | 相同请求；时间/实体/投影改变；刷新；只用旧结果 | 命中与拒绝各有正确证据，不错误替换查询语义 |
| 数据完整性 | 完整TopK、真实空结果、分页/截断预览、缺稳定键 | 保留各自语义，预览不能冒充全集 |
| 交付 | 模型只选一个问题；隐藏中间计算；非表格口径回答 | 每个原问题有交付或状态，不强迫展示所有中间表 |
| 恢复隔离 | 部分澄清、完成后恢复、同轮重试、并发、Scope/目录版本变化 | 不重跑已确认结果，不串会话、不扩大授权 |
| 资源与异常 | 达到/超过预算、ASL/SQL超时、不可重试语义错误 | 有界且可解释；只重试应重试节点，保留健康分支 |
| 可见合同 | 规划完成前无工具输出；各任务状态和现有主节点 | 节点名称/顺序和已验收回答行为不被内部优化改变 |

## 8. 范围、测试与发布约束

1. 功能修改前重新检查工作目录、Git状态及远端差异，防止覆盖同步后其他人的代码。先把本轮复现变成针对当前真实入口的回归用例，再做最小修复。
2. 本轮研究没有发现必须立刻修改Oagnet或SQL Translator的确定根因。跨服务仅验证合同；发现具体根因后在所属服务修，不能在Agent侧掩盖上游缺陷。
3. 测试按改动范围覆盖专项、Critical、相关全量/接口验证，记录baseline/final、收集错误和新增回归。已有无关失败保留分类，不能为清零而删除或弱化断言；也不能因全库历史失败而无限扩张当前目标。
4. 按明确清单同步到版本仓并校验SHA-256，保护配置、凭据和用户改动；创建功能提交、功能分支及Draft PR，不自动合并。通过相应测试后，按已有授权部署49受影响服务并验证健康；测试失败、冲突或权限不足时停止发布并说明。
5. 不包含：框架迁移、通用任意代码执行器、无上限递归重规划、全量AST替换、全目录身份重建、语义库改写/索引重建、V2切流、全面消除旧测试失败或性能平台改造。
6. 用户本轮提供的六主节点名称与顺序是最高优先级验收合同：`意图识别 → 任务拆分与规划 → 调度执行 → 结果校验 → 数据洞察分析 → 最终输出`。子目录AGENTS另有七节点历史文字，当前源码包含解析校验；源码存在某步骤不等于它已获当前主节点合同认可。后续验证须区分主节点与内部步骤，验证六主节点名称和相对顺序，不自行把解析校验提升为第七主节点。若当前可见行为与合同不符，保留复现并单列问题，不借阶段1的执行修复顺带增删SSE节点，也不宣称该项已验收。
