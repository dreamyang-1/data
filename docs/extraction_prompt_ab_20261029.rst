结构化参数提示词迁移前后对照（2026-10-29）
========================================

结论
----

PROVEN：只改变参数提取提示词，模型输出的去重、限制和实体选择仍会变化。
两版没有修改“是否去重”的文字规则；变化发生在模型对任务类别的理解上。
不能据此说所有历史失败都是本次提示词迁移造成，也不能说恢复旧提示词就全部正常。
本次只同步代码和做对照，没有修复业务逻辑、回退生产提示词或部署实验版本。

华山产品去重的具体证据
--------------------

原问题：2025年复旦大学附属华山医院销售订单金额最多的销售员是谁？销售了哪些产品？

两版 PARAMETER_PROMPT 和 EXTRACTION_PARSER_PROMPT 中所有包含“去重”的规则行相同。
原规则要求：名单或属性信息去重，交易流水明细不去重。
规划任务却写成“向该院销售的全部产品明细”，交付物包含产品名称、编码等“明细信息”。
这个表达没有明确区分产品名单与销售流水，给参数提取留下了再次判断的空间。

固定上下文的结果如下：

.. list-table:: 同样的任务输入，仅提示词版本不同
   :header-rows: 1
   :widths: 28 24 24 24

   * - 输入来源
     - 旧版输出去重
     - 新版输出去重
     - 新版输出不去重
   * - 新版首轮的真实上下文
     - 6/6
     - 1/6
     - 5/6
   * - 旧版首轮的真实上下文
     - 6/6
     - 5/6
     - 1/6
   * - 合计
     - 12/12
     - 6/12
     - 6/12

两个上下文摘要分别为
``5e7cca3166110786c1ae18e51c8b90f57ea22e5fa524c33dedf0d61dbd270d12``、
``7d14ccabc9bdd45084dddf05532b933ebe2c114c106e88934c2638d35e6ca1bc``。
统计是本次有限样本，不能当成线上故障概率。

完整执行的三轮结果：旧版产品行数依次为 926、0、926；新版为 926、926、436。

* 新版第三轮确实复现漏产品：提取“是否去重=否、限制=1000”，
  SQL 没有 DISTINCT，先截取 1000 条流水，再清理重复记录，最终只剩 436 种产品。
  这与先在数据库去重再取产品名单不是一回事。
* 新版第二轮同样没有 DISTINCT，但限制为空，执行侧取 10000 行后，
  本次结果中仍得到 926 种产品；不能因此说“不去重”没有风险。
* 旧版第二轮返回空结果的原因不同：模型凭空生成
  ``__DEPENDS_ON_TASK_0__`` 作为销售员编码。
  SQL 同时要求编码等于该占位符、又属于前序真实入选编码，两个条件冲突。
  日志证明是假编码条件造成空结果，最终回答却归因于数据水位，解释也不准确。
  这说明旧提示词也有缺陷；该次完整执行的上游措辞并非逐字相同，
  因而不能仅凭这一次认定“只有旧提示词会生成假编码”。

PROVEN：去重结果在相同动态输入下仍随提示词版本变化；新版在完整执行中出现
未去重先截断的漏数。HIGH_CONFIDENCE：任务中的“产品明细”与“名单/流水”分类边界
是输出不稳定的一个关键条件。UNKNOWN：三段职责说明和计算说明中具体哪一句
造成多大贡献；本次没有做逐句消融，不能编造模型内部原因。

未覆盖的历史场景
----------------

回归清单另有9项未纳入本次聊天提示词对照，不能声称全部历史场景都已验证：

* “过滤条件有指标字段，但是指标字段为空，没有值”：缺完整原问题和范围。
* 经销商前三名问题恢复旧合作时长澄清：缺原会话前序上下文；新会话不能代替。
* “合作最早的经销商，它的订单总金额是多少？”：缺原请求范围和上下文。
* “全部历史订单金额最大的一笔订单是哪一笔?”恢复旧澄清：缺前序会话和范围。
* 医院与科室关系推荐：原实体ID省略，缺范围。
* 模型122实体关系推荐为空：是推荐接口问题，不经过本次聊天参数提取提示词，未混入聊天验证。
* 城市与省份关系推荐：缺模型、域和实体ID。
* 国药公司与销售员关系推荐：缺模型、域和实体ID。
* 发布失败中文化：缺原发布参数，且不是本次只读查询范围。

如果后续要修复，应先明确本任务交付的是哪一种结果，再保证取数、去重和限制顺序与之吻合。
