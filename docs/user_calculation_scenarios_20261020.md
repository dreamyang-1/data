# 用户问法、计算及依赖链路审查（2026-10-20）

本轮设计13组用户问题，检查意图识别、规划边界、结构化参数、ASL、SQL、计算数据集、校验、洞察与最终答复。验收同时检查数值和对象范围，不能把 COMPLETED 当成正确答案。业务记录仅在服务器内存中与独立只读SQL核对，保存的证据仅含问题、阶段状态、计数、字段及核对布尔值。

## 已证实的根因与最小修复

1. **纯数字入口只接单次运算。** PROVEN：加法后再除法、括号表达式和并列计算均被判为 OUT_OF_SCOPE，规划和计算没有执行。新增有限数值语法编译，将运算顺序和括号转成原有受控步骤；仍不执行任意代码，不把业务字段当常量。沿用最多5步流水线，其中最多4步计算及1步结果投影。除零返回明确失败，四舍五入显示保留指定小数位，保存的数据仍是数值。
2. **模型结构与执行结构缺少统一规范化。** PROVEN：P90被输出为 `params.p=0.9`，执行器忽略嵌套参数后使用默认P50；独立核对确认请求虽完成但数值错误。相关系数的 `right_field` 与 `other_field`、流水线的 `pipeline/steps/operations`、筛选与投影的不同写法也会阻断执行。现在在计算合同边界统一已知写法，概率p只接受0至1，冲突和未知统计参数明确报错，不静默使用默认值。参数提取不再以另一种拼写覆盖规划的实际含义。
3. **聚合破坏样本行，计划又没有证明比较列已经产生。** PROVEN：先汇总均值会丢掉各业务员；另一轮计划只在取数任务描述里承诺“平均订单笔数”，实际未生成该列。新增保留原始行的聚合及列对列比较，均值可附在完整样本上后再筛选；规划阶段检查比较列来源，遗漏计算时纠错，不等到SQL执行之后才发现。普通统计聚合行为保留。
4. **有图依赖仍不代表参数真的被传递。** PROVEN：明确标号三连问的依赖已是 `task-1 → task-2 → task-3`，调度器却只用旧指代词表决定是否传参。“问题一选出的业务员”不在词表，第二问查询了全部89人，第三问对错误范围求和，三项任务都显示完成。现在问题/任务编号及上一问的指代由统一解析器识别，前置补键、参数编译共用同一锚点；题目标题和单纯“等待任务完成”的控制顺序不会自动产生名单筛选。另按已验证SQL的列绑定选择身份键，避免“业务员 ID”等别名导致误选姓名。
5. **必需展示字段在两个服务间丢失。** PROVEN：Agent已提取“销售员姓名”，但指标查询的出站合同未保留该字段，原有完整性检查因此正确拦截。修复合同传递，同时保留聚合中订单号等身份键必须成为分组的约束。随后发现ASL生成也会遗漏目录唯一确认的姓名字段；仅扩展既有元数据补全步骤，补齐明确要求且唯一可解析的展示字段。未恢复整套旧修复逻辑，未修改ASL/向量校验和业务值标准化函数；候选不唯一时不擅选，继续交给现有校验。

## 各阶段核查标准

- 意图与规划：纯数值问题进入确定性计算；查询、后续取数和本地计算分别声明依赖；独立问题不继承彼此的粒度、筛选和Top N。
- 解析：字段和值使用当前授权目录；明确保留百分位点、成对字段及总体/样本口径。新生成的计算列不冒充数据库指标。
- 执行：名单消费完整、质量通过的数据集，按已证实的身份字段传递；后续新指标重新查询，已有数据直接计算。核对Top5入选范围及89人取样后高于均值名单的全部18人。
- 校验：用独立只读SQL及数学定义核对中位数/P90、相关系数、月度金额比值、方差开方和标准差、名单及合计，不仅检查状态。
- 洞察与输出：答复覆盖各项业务要求；除零解释原因，空样本不伪造标准差0。所有问题按冻结7节点顺序展示，纯计算不调用SQL。
