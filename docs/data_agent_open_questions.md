# 需要业务方确认的信息

以下问题无法仅凭当前代码、配置、测试和历史评测结果确认；未重复列出代码已经给出明确答案的事项。

1. 生产环境实际加载的模型供应商、精确版本和运行参数，是否与当前本地配置 `qwen3.6-plus`、意图温度 0、闲聊温度 0.5 一致？
2. 各 `PrimaryIntent` 的正式业务必填槽位是什么？尤其是：聚合查询能否无维度、明细查询能否无 `fields`、销售额是否必须有时间。
3. “销售趋势”默认成“销售额趋势”和未指定时间默认最近一年，是否已经获得业务口径批准？是否允许其他默认指标或默认明细字段？
4. 向量检索的唯一 Top1 是否允许自动采用？业务可接受的误规范化率、错误继承率、不必要追问率分别是多少？
5. 单请求和复合请求的延迟 SLA、模型调用成本上限，以及是否允许为轮次关系增加一次轻量模型调用。
6. 原始消息是否允许由后端长期保存，允许保存多久；当前客户端是否保证同一会话持续复用 `conversation_id` 并正确携带 `history`？
7. Redis 短期状态是否应在读取时滑动续期；超过当前 2 小时 TTL 的任务是否仍必须可连续追问？
8. 用户是否应有关闭短期记忆、长期偏好和删除整个 conversation 关联状态的产品入口？
9. 第三方模型供应商处理业务问题、汇总事实和可选工具参数时适用的合规条款、数据驻留和保留策略是什么？
10. 是否存在可供审计的生产失败日志和人工标注的正确查询契约（轮次关系、槽位、继承、ASL、结果列）？仓库内评测产物多数没有完整 trace。
11. 是否正式支持多语言输入、同一句多个独立查询、多数据源跨库查询，以及单任务多个指标/多个维度？
12. dataset 结果操作的完整产品范围是什么：除排序、TopN、筛选、投影、聚合、差额、导出外，是否还要求 join、窗口计算或跨 dataset 计算？
13. 当前业务最常见失败场景和“追问过多”场景的业务优先级排序是什么？
14. Redis 连接是否必须使用 TLS、静态加密和专用 ACL；MinIO/MySQL 的加密、备份和删除合规要求是什么？代码只能证明连接参数，不足以证明部署侧安全策略。
15. 前端是否可能每轮重新生成 `conversation_id`，以及 refresh/revise 时能否总是提供准确的 `replaces_message_id`？
