# 关系推荐删除恢复修复

## 根因与修复边界

**PROVEN（代码与只读快照回放）**：候选依赖已配置关系以及主表的 `id/*_id` 命名推导。真实删除会移除已配置关系；业务编码关联、无 `id` 主键表，以及实体子表上的关联无法重新推导。因此，候选消失不能直接等同于数据库未删除。

仅修改数据智能体的 Python 推荐实现，增加当前模型、数据源内的业务键与有效子表映射推导。`*_code/*_no/*_key/*_id` 只产生待确认候选；同名字段不能证明唯一性，不再据此断言多对多。数据类型不兼容或来自其他数据源时不产生候选。重复物理字段优先采用已有配置基数。多个独立外键分别推荐，不再合成一个无法完整保存的关系。

旧配置只保存列名时，只在对应实体的已映射表中唯一匹配；不能唯一确认则保留未解析状态。修正一对多描述的反向数量。保留本地既有两跳推断，但不把基数未知的新候选升级为已确定的两跳证据。

用户本轮明确限定“只能改数据智能体”。此前尝试的前端、Java 修改已逐文件恢复至开工快照，SHA-256 校验一致；仅删除本轮新建的两个测试文件，保留原有未提交改动。最终不包含前端或 Java 变更，也没有发布这两个组件。

前端重复确认、异步响应与预填时序，以及多字段保存等问题不属于最终修复范围，不能宣称已经解决。数据智能体只提供只读推荐，不能替代业务后端执行实体删除或修改数据库记录。

## 验证

- Python 推荐及新增恢复测试：67 项通过。
- 服务器现有功能基线上的最小候选补丁：58 项通过。首次隔离运行受服务器环境的运行模式影响，随后按仓库离线测试合同仅在测试进程设置 V1；未切换服务运行模式。
- Critical 两个切片：23 项通过。
- 两个只读元数据快照共 36 组关系，原规则删除重建后 26 组为空；修复后恢复相同主表和子表映射，36 组均能再次产生候选。全部删除与重建仅发生在内存副本中。这证明候选恢复，不证明每个候选的业务含义或基数已被确认。
- 全量 baseline/final 逐项差异及发布结果见 `verification.json`。保留基线失败，不宣称全库通过。

## 发布与集成

Agent 开发目录与服务器存在既有功能差异。`server-service.patch` 只包含本次共同调用链的修复，保留服务器原有功能范围，不借此发布本地尚未上线的两跳功能。补丁基线及结果 SHA-256 记录于 `integration_manifest.json`。

前端与 Java 工作区已有其他未提交改动。本轮增量已全部撤回；其原有工作树与暂存区不受本次数据智能体提交影响。

**PROVEN（发布包检查）**：用户指定页面当前公开资源已经携带删除模型参数，但未包含本地新增的关系推荐弹框；对应后端发布类也没有本地推荐方法。检测记录表在检查的两个模型中没有记录，不能认定是其 `configured` 标志残留造成问题。

**UNKNOWN / 验收边界**：该页面用户实际操作时所加载资源与当前下载发布包的对应关系尚未建立；前后端整包不与本地源码基线一致。没有覆盖该服务的部署包，不能宣称该页面已完成真实浏览器新增、删除验收。最终仅验收数据智能体的推荐实现及接口。

## Code Review

没有读取已删除关系来“恢复”候选，没有修改业务库，也没有把同名字段当成已验证关系。模型只能修饰候选名称，不能将未知基数改写成确定数量。每个子表必须属于当前实体的有效映射。三个旧断言属于 `STALE_TEST`：两处一对多反向描述错误，以及一处仅凭同名字段断言多对多；已根据关系基数含义改正并加入正反例。其他既有测试保持通过。

未修改语义数据库、索引、授权规则、ASL 向量标准化规则、分析编排或其他窗口负责的功能。
