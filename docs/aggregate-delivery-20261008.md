# 排名计算与关联展示字段修复 — 2026-10-08

## 根因（PROVEN）

1. 聚合查询把“人员所属公司”误当成必须新增的分组维度，拒绝了目录中明确的 N:1 关联属性。
2. 纯计算失败会退回模型文字并标记成功，没有实际计算数据集。最终报告可能选择原始统计表，文字说前五名，表格却是所有人员。
3. 旧规划校验只认识阿拉伯数字排名；“降序取前五名”被误判成遗漏排名目标。计算指标后面的括号说明也会干扰名称识别。
4. 公司查询成功后，排名分析把业务员/销售员名称视为不同对象，并在最终排名表只保留标签和数值，丢弃公司属性。
5. 扩大对象识别后，复测暴露出调度顺序的旧缺陷：明确的纯计算任务仍可能先被送进关联查询条件编译。已将“不再查询数据库”的分支提前，仍由受控计算器验证能否执行。

## 修改清单

- Oagnet：`structured_binding.py`、`agent.py`。目录中的唯一关联展示属性进入内部 `display_fields`；仍核对授权向量字段。不改变原本的分组维度，不猜测多值关系。
- SQL Translator：`sql_translator_prod.py`。独立验证展示字段和 N:1/1:1 关系，生成 SELECT/JOIN/GROUP BY；拒绝未注册字段和会造成行数膨胀的关系。
- DataAnalysis：`app/adapters/http.py` 展示关联字段；`app/planning/task_dag.py` 保留公司、时间与最终排名目标；`app/planning/calculation_targets.py` 识别明确声明的计算目标。
- `app/services/dataset_followup.py`：订单平均金额/平均订单金额/客单价由金额除以订单笔数确定性计算，按用户方向和人数处理。
- `app/services/computation_delivery.py`、`app/services/orchestrator.py`：完整输入执行受控计算，保存实际最终结果；同粒度多数据集只按唯一编号对齐，不按姓名或行号拼接；失败不让模型文字冒充成功。
- `app/analysis/engine.py`：统一人员名称别名，保留已绑定的关联展示属性和身份编码。
- `app/presentation/root_report.py`：真实完成的计算结果取代其依赖的中间统计表，不能被模型选表建议回退。

新增测试：`Oagnet/tests/test_aggregate_display_fields.py`、`sql-translator/test_aggregate_display_fields.py`、`tests/test_computation_delivery.py`、`tests/test_aggregate_ranking_label.py`。

## Review 与发布边界

聚合粒度由已绑定的身份维度确定；关联属性仅沿目录中的唯一关系展示，不使用 MIN/MAX 任取一个公司。指标公式、时间筛选、SQL 只读限制、执行超时和既有 JOIN 安全措施不变。完整输入不等于无限查询，用户明确的 LIMIT 仍生效。

多值或未知关联不在人员排名中隐式展开。没有完整数据或受控操作无法实现时明确失败并保留已完成的查询结果，不伪造计算、排序或筛选完成。

正式运行环境已有额外的规划保护、语义说明加载和输出简化；采用共同基线三方合并保留这些行为。规划器冲突只合入上述两条规划规则、明确计算目标识别和排名表述修复，不覆盖整份远程文件。

对外接口、进度节点顺序、授权范围及 V1/V2 路由不变。不修改语义数据库，不重建向量索引。逐文件同步、部署前再次核对远程基线、备份受影响代码并保护配置。
