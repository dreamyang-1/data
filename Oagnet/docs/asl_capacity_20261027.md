# ASL 并发与异步排队（2026-10-27）

## 改动

原默认容量为 1 个执行槽位与 8 个等待名额。同步 HTTP 路由等待信号量和工作线程，扩大队列会持续占用 Web 线程池；模型 SDK 没有网络超时。

本次改为单一有界 FIFO 调度器：HTTP 异步等待，只有已经获得执行名额的任务进入专用线程池。同步 `run` 与异步 `arun` 使用同一调度实现，没有保留旧信号量队列作为回退。等待请求取消后移出队列；已经运行的请求取消后，工作线程实际结束前仍占用执行名额。取消后不再启动下一次限流重试。

工作线程接收每个请求独立的 ContextVar 上下文；排队和执行计数由锁保护，支持来自不同事件循环的调用。保留接口路径、请求/响应合同、429 错误码和 Retry-After。没有修改字段、条件值标准化、Scope、目录绑定、ASL 生成逻辑或 Agent 节点编排。

| 配置 | 默认值 | 含义 |
| --- | --- | --- |
| `OAGNET_LLM_MAX_CONCURRENCY` | 4 | 每个进程实际执行的 ASL 请求上限 |
| `OAGNET_ASL_MAX_WAITERS` | 32 | 每个进程等待人数上限；允许配置为 0 |
| `OAGNET_LLM_CONNECT_TIMEOUT_SECONDS` | 10 秒 | 模型连接及连接池等待超时 |
| `OAGNET_LLM_READ_TIMEOUT_SECONDS` | 120 秒 | 模型网络读取及写入超时 |

120 秒是待进一步观察调整的初始保护值，未声称来自完整生产延迟分布。SDK 网络超时不是端到端总截止时间；正常排队仍不设置总时限。旧的“SDK timeout 必须为 None”断言按用户本次批准的方案迁移，正常无限排队合同仍有测试保护。

通过 `app.capacity` 日志记录队列等待时间、工作耗时、执行数、等待数、完成/失败/取消数、本地拒绝和上游限流次数；不记录业务输入、凭据或数据行。容量快照可通过控制器 `snapshot()` 读取。没有增加公开管理接口。

第一阶段只做单进程共享 FIFO，不增加调用方身份协议、配额体系、Redis 队列或多个 worker。现有调用方不能仅凭任意 HTTP 头取得可信服务身份。多实例下总并发是各实例并发之和，部署前须另行核对上游额度。内存队列不保证跨进程重启恢复。

## 原问题与发布边界

修改前在原 Agent HTTP 入口按既有历史运行器的模型 130、原应用范围执行了 12 项历史问题，采用 2 路有界并发与独立会话。11 项首轮返回 HTTP 500；“当前语义模型中建立了哪些实体”正常完成。首轮失败的多轮问题，其后续响应不计作有效多轮通过。清单中另外 5 项 unresolved_context 没有完整验收；其中发布写操作不属于本次只读范围。

错误在进入 ASL 前发生：`app/structured_extraction/extractor.py` 导入 `app.planning.metric_thresholds.normalize_metric_units` 失败。用户确认该调用链由其他任务修改，要求本次先完成 ASL 代码和隔离验证。

因此本次未覆盖该 Agent 调用链，未安装候选到正式服务，未重启或修改生产配置，未执行语义库写入、索引重建、业务写入、V2 切流或自动合并。部署后的原问题完整验收与历史并行回归均未完成；不得宣称线上并发已提升或所有业务问题已恢复。

后续应在其他任务修复入口后，重新核对远端差异、上游额度和参数覆盖，验证完整业务链，再按受保护的发布流程部署与复验。
