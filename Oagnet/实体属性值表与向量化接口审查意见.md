# 实体属性值表与向量化接口审查意见

> 审查对象：`semantic_model_entity_att`、Oagnet实体属性值向量化接口、问题改写与ASL生成检索链路  
> 审查日期：2026-08-24  
> 数据库操作：仅只读检查，未修改表结构和数据

## 1. 审查结论

当前表已经具备首批数据写入所需的基础字段，新接口也已完成“按语义模型和业务域读取、向量化、作用域覆盖、检索并注入ASL提示词”的闭环。但是，表结构目前只适合联调，不建议直接作为生产契约。

上线前最少需要完成：关键字段非空、权威实体/属性ID、标准属性值编码、作用域索引、业务唯一约束、敏感值准入规则和接口鉴权。

另需明确：`semantic_model_id + business_domain_id`限定的是语义作用域，不是会话。会话仍由`conversation_id`识别。

## 3. 必须整改的问题（P0）

### 3.1 缺少权威业务对象ID

只保存`entity_name`和`attr_name`会在重名、改名、历史版本场景中失去稳定关联。建议新增：

```text
entity_type_id       varchar，关联 semantic_model_entity_type.id
attribute_config_id  varchar，关联 semantic_model_attribute_config.id
```

数据库是否建立物理外键可由数据团队决定，但写入服务必须验证ID、语义模型和业务域属于同一作用域。

### 3.2 缺少标准属性值编码

当前只有`attr_value`展示文本。ASL过滤通常需要稳定编码，建议新增：

```text
attr_value_code  标准编码，例如 EAST_CHINA
aliases          别名JSON，例如 ["华东区", "东部地区"]
```

推荐一行一个标准值，禁止用逗号把多个值拼在一行。

### 3.3 关键字段允许为空

以下字段应为`NOT NULL`：

```text
semantic_model_id
business_domain_id
entity_type_id
attribute_config_id
entity_name
attr_name
attr_code
attr_value_code
attr_value
is_deleted
```

### 3.4 缺少作用域索引和业务唯一规则

至少增加作用域索引：

```sql
CREATE INDEX idx_entity_att_scope
ON semantic_model_entity_att
   (semantic_model_id, business_domain_id, is_deleted);
```

建议的逻辑唯一键：

```text
semantic_model_id
+ business_domain_id
+ entity_type_id
+ attribute_config_id
+ attr_value_code
```

软删除与唯一索引的实现方式需要数据团队统一设计，避免删除后无法重新创建同一标准值。

### 3.5 缺少敏感和高基数数据准入规则

允许向量化：地区、状态、渠道、类别、门店类型等低敏感、低基数业务值。

禁止向量化：姓名、手机号、证件号、客户ID、订单号、流水号、精确地址、连接串、密钥，以及数十万级实时商品/交易明细。高基数实体应使用受控实体搜索或数据库精确查询。

## 4. 建议完善的问题（P1）

建议增加：

```text
status           DRAFT/PUBLISHED/DISABLED
version_no       语义版本
valid_from       生效时间
valid_to         失效时间
source_type      MANUAL/IMPORT/DATABASE
source_batch_id  数据批次
project_id       可选，用于审计和快速过滤
```

向量只应读取已发布、当前有效、未删除的数据。当前接口暂时只能依据`is_deleted=0`过滤。

## 5. 现有基础语义数据质量观察

本次只读统计时：

- 有效实体记录296条，其中16条缺少`semantic_model_id`，也无法与“同一语义模型下的业务域”形成有效关联。
- 有效实体中10条缺少实体编码，181条缺少描述。
- 有效属性记录980条，其中13条缺少属性编码，813条缺少描述，3条缺少物理字段映射。

以上数字会随数据更新发生变化，但说明填充新表时不能直接复制所有旧数据；需要先校验作用域、编码和映射。描述缺失不会阻止向量化，但会明显降低语义召回和消歧质量。

## 6. 已实现接口

数据侧正式触发接口为同步接口：

```http
POST /vector/entity-attributes/sync
Content-Type: application/json
```

请求：

```json
{
  "semantic_model_id": 5,
  "business_domain_id": 9,
  "event_id": "entity-att-20260824-001"
}
```

接口会等待MySQL读取、数据校验、Embedding和索引覆盖全部完成，再返回HTTP 200。成功响应包含读取行数、索引行数、覆盖行数、删除行数、`event_id`和完成时间。失败会在本次调用中直接返回4xx/5xx，旧索引保持不变。同一个更新批次重试时必须复用相同`event_id`，单进程内会直接返回第一次成功结果，避免重复向量化。

所有失败响应都包含统一的顶层标志：

```json
{
  "success": false,
  "detail": {
    "code": "ENTITY_ATTRIBUTE_SOURCE_INVALID",
    "message": "该语义模型和业务域下没有实体属性值，已保留旧向量数据"
  }
}
```

参数格式校验失败时`detail`仍为FastAPI标准错误数组，但同样包含`"success": false`。这样数据侧可以先统一判断`success`，再根据HTTP状态码和`detail.code`处理具体错误。

作用域状态查询：

```http
GET /vector/entity-attributes/status?semantic_model_id=5&business_domain_id=9
```

旧重建接口继续保留用于内部兼容和小规模运维：

```http
POST /vector/entity-attributes/rebuild
Content-Type: application/json
```

请求：

```json
{
  "semantic_model_id": 5,
  "business_domain_id": 9
}
```

成功响应包含：读取行数、索引行数、覆盖行数和删除旧向量行数。

接口行为：

1. 校验两个ID为正整数。
2. 校验业务域属于指定语义模型。
3. 只读取当前作用域未删除的数据。
4. 校验主键、作用域、实体、属性编码和属性值。
5. 拼接实体名称/别名/描述、属性名称/编码/描述和属性值进行Embedding。
6. 写入`entity_attribute_value`类型向量。
7. 新向量写入成功后，删除当前作用域已不存在的旧记录。
8. 不影响其他作用域和其他向量类型。
9. 空表、字段缺失或Embedding失败时保留旧索引。

当前目标表为空，调用会返回HTTP 422和`ENTITY_ATTRIBUTE_SOURCE_INVALID`，这是预期的安全行为。

## 7. ASL生成链路核验

已确认`PromptBuilder`会额外检索`entity_attribute_value`，且查询条件同时包含：

```text
type=entity_attribute_value
semantic_model_id=<当前模型>
business_domain_id=<当前业务域>
```

召回结果会与实体知识一起进入提示词，供问题改写和ASL过滤条件生成。未指定业务域时会检索该语义模型下所有业务域，因此平台调用时应尽量提供准确的`business_domain_id`。

### 7.1 在线实体属性检索接口

同步更新接口只负责刷新索引，不能用于在线问题匹配。现新增只读接口：

```http
POST /vector/entity-attributes/search
Content-Type: application/json
```

```json
{
  "query": "查询北经区域本月销售额",
  "semantic_model_id": 5,
  "business_domain_id": 9,
  "top_k": 5,
  "score_threshold": 0.70
}
```

接口严格使用`semantic_model_id + business_domain_id + type=entity_attribute_value`过滤，返回实体名称、实体别名数组、属性名称、属性编码、标准属性值和相似度。它只返回候选，不直接篡改用户问题；自动改写决策由数据智能体的改写安全门完成。

职责必须分开：

- `POST /vector/entity-attributes/sync`：数据侧数据提交完成后，同步刷新向量索引并返回最终结果；
- `POST /vector/entity-attributes/search`：用户每次提问时在线召回规范化候选。

## 8. 接口仍需改进的地方

### 8.1 同步接口幂等结果目前保存在进程内

同步执行和MySQL跨进程互斥已经实现，`event_id`成功结果缓存在Oagnet进程内。但服务重启后幂等记录会丢失，多实例也不能共享已完成结果。生产版应将`event_id + semantic_model_id + business_domain_id + 最终结果`保存到Redis或MySQL：

```text
POST /vector/entity-attributes/sync -> 等待执行完成 -> 200 + 最终统计
```

### 8.2 缺少接口鉴权

当前接口如果直接开放在内网，任何能访问端口的调用者都可能触发昂贵重建。生产前应由Java网关或服务Token限制调用方，并记录调用者、批次和trace_id。

### 8.3 Chroma覆盖不是完整事务

当前安全顺序为“先写新记录、成功后删旧记录”，已经避免空表或Embedding失败误清空。但Chroma不提供跨upsert/delete的数据库事务。更高要求下建议使用`index_version/source_batch_id`构建新版本，完成后原子切换活动版本，再异步清理旧版本。

### 8.4 日志保护

已删除完整Prompt的控制台输出和日志输出，避免实体属性值随提示词写入日志。仍建议继续审查用户原问题和完整ASL日志，按敏感等级决定脱敏或仅记录指纹。

### 8.5 Windows多进程日志滚动

测试时观察到已有服务进程占用`logs/app.log`时，另一个进程触发`TimedRotatingFileHandler`滚动可能出现文件占用错误。接口仍能完成，但生产日志可能丢失。建议采用单进程文件写入、集中日志采集，或支持多进程的日志处理方案。

## 10. 数据侧联调建议

建议数据侧先写入10～50条非敏感样例，至少覆盖：

1. 同一属性多个标准值。
2. 属性值别名。
3. 不同业务域存在相同文本值。
4. 同一实体下多个属性。
5. 删除、改名和重新发布。
6. 重复数据拦截。
7. 空值和非法作用域拦截。

写入事务提交成功后，再调用向量重建接口。联调问题至少包括：

```text
查询华东地区本月销售额
只看已支付订单
分析直营网点的订单趋势
华东是地区还是门店名称
```

验收应检查：召回作用域正确、标准编码正确、ASL字段映射正确、不同业务域不串数据、删除值不再召回、敏感值不进入向量库。

## 11. 建议实施顺序

1. 数据侧确认实体属性值业务唯一键。
2. 增加实体ID、属性ID、属性值编码和属性值别名；现有`entity_alias`只是实体别名，不能代替属性值别名。
3. 将关键字段改为非空并增加作用域索引。
4. 制定敏感和高基数值准入规则。
5. 写入少量样例并完成真实Embedding/召回/ASL联调。
6. 增加接口鉴权、共享任务状态和版本化索引切换。
7. 完成批量数据导入和回归评测后再发布。
